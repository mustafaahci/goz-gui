# The Win32 boundary (`src/win`)

goz-gui is `#![deny(unsafe_code)]`. Every `unsafe` block is in `src/win`, a layer of safe functions over `windows-sys` and the `windows` crate's COM interfaces. The rest of the crate calls Windows only through it. This page is for anyone who adds a call to Windows: what the layer promises, and how to extend it.

## What "safe" means here

A safe function in `win` must be sound for **every** argument safe code can pass. The layer's trust model (also at the top of `src/win/mod.rs`):

- **The system checks its handles.** user32, gdi32, comctl32, shell32 and ole32 report a stale or wrong `HWND`, `HDC`, `HMENU`, `HICON`, `HACCEL` or GDI object as an error; they never follow it as a pointer. Those handles are plain `Copy` values, and any value is a valid argument. Two kinds of handle are not checked, and are types instead:
  - An **image list** (`HIMAGELIST`) is an `IImageList*` that every call follows. A list is an `imagelist::ImageList` (owned; its clones are the same list, destroyed with the last) or an `imagelist::SystemList` (the shell's, one reference kept for the process). Nothing takes a raw one or destroys one. A list view given an owned list takes it whole (it destroys its lists with itself) and gives back, destroyed, the one it had from goz-gui; a system list goes to it with a reference of its own; a tree, which destroys none, has the one it shows kept by goz-gui until it shows another or is gone. What a control shows, takes and gives back is asked of its class's own procedure (below), after each giving (one may be nested in another, from a notification the control sends as it takes a list), and `lv::draw_image` draws only from the list the list view itself answers it shows. A list a control gave back or no longer shows is let go only once the control is done with the giving that ended its use.
  - A **tree item** (`HTREEITEM`) is an address in its tree that comctl32 checks only by a signature, never against the tree it is sent to. Items are `tv::Item`s: only `tv` makes one (inserts, the tree's answers, hit tests, notifications of the tree), each names its tree, and every function taking one acts on that tree. A tree is kept track of from its birth: `class::create_plain`'s, adopted as it is made, or a `dlg::Template`'s, seen by a CBT hook as the dialog manager makes it (another tree view, whose past is not known, is taken by none of `tv`'s functions on items). Every `tv` message naming an item goes to the tree's class's own procedure, so no subclass runs between the check that the item is in the tree and the tree's reading it (a subclass could delete it, then pass the message on). An item is noted as `tv::insert` puts it in, by the tree's own answer; each deletion (TVM_DELETEITEM of an item or of every item, a collapse-reset of an item or of the top, the tree's end) takes its items out of the record before the tree sees it, `tv`'s own and, by a subclass put in as the tree is made, another's code's through the window (an item not noted is refused there: it may be one a subclass in front already passed on a deletion of). So an item is refused from the moment its deletion starts, and while a deletion is under way the tree takes no insert, deletion or reset of goz-gui's. A tree is busy while it is in its own processing as far as goz-gui sees (a message passing that subclass, a call of `tv`'s to its class's procedure: every one goes through a `Busy`), when it may be using any of its items (the one a notification is about, the one it draws, selects or was clicked on), and comctl32 does not survive each being deleted under it: a deletion `tv` is asked for meanwhile (`tv::delete_item`, `tv::delete_all`, from a notification handler, say) waits until the tree is out of it, its items refused from the moment it is asked for, and a collapse-reset is refused. After a deletion passed on, the record is changed and the tree walked only if the window is still the same tree (a record's serial; the class's procedure looked up again): another's code may have destroyed it meanwhile, and its handle be another window's since. Another's code's message that names an item (TVM_GETITEMW, TVM_EXPAND, an insert's parent...) comes through the window's subclasses, any of which may delete the item before passing it on: each pass of one by a subclass of goz-gui's (`m.def()`) checks every item it names (in its parameters, or copied from the structure its `lParam` points at) against the record first, and stops the message, answering 0, if one is not there (special handles, TVI_ROOT and the like, are no items, nor is 0 where the message means none by it). The check is at every pass, so the last one before the tree is made whatever the order of the subclasses (one put in at the tree's birth is nearer the tree than the one that keeps track of it). A stale item names, at worst, a new item the same tree put at its address: wrong, not unsound.
- **A window is destroyed only out of the processing of the controls in it.** A window's handle is checked, but a control destroyed in the middle of an operation of its own (sending its parent a notification as it deletes items, expands one or moves its selection) goes on using the memory it freed, and the common controls do not survive it. goz-gui's code runs inside such an operation only where a trampoline hands it a message, and each holds the control busy while it runs (`busy`): a window's, dialog's or subclass's procedure handed a message a control sends its parent (WM_NOTIFY's `hwndFrom`; WM_COMMAND's, WM_CTLCOLOR*'s, WM_HSCROLL's and WM_VSCROLL's control; WM_DRAWITEM's, WM_MEASUREITEM's, WM_DELETEITEM's and WM_COMPAREITEM's; the child of a WM_PARENTNOTIFY or a WM_CONTEXTMENU), a subclass passing a message on to a control's own procedure (`m.def()`), `queue::dispatch` handing one to a control, a hook's closure (the window a sent message or a CBT event is about, the control it comes from), `tv`'s calls to a tree and the messages passing the subclass that keeps track of it. `win::destroy` of a window that is or holds a busy control (a child, an owned window, theirs: what DestroyWindow destroys with it) does not destroy it then: it posts to a message-only window of the layer's on that thread, which destroys it once the stack has unwound, if it is still there and nothing in it is busy (`win::destroy` answers true meanwhile). A window of goz-gui's answers WM_CLOSE the same way (`m.def()`), and `win::send_plain`, `win::post_plain` and `win::post_close` send WM_CLOSE and WM_SYSCOMMAND only to goz-gui's own windows, as another window's default processing of them destroys it at once. Modal dialogs end with `dlg::end` (EndDialog, which the dialog manager carries out once its loop has control back). Left to the controls, as any Win32 program leaves it: a control with no subclass of goz-gui's in a loop of its own (a drag's) entered from a loop that is not goz-gui's (a modal dialog's, a menu's), while the handler of a message dispatched there destroys a window holding it; and a WH_GETMESSAGE or low-level keyboard hook's closure doing so while a control waits for input in such a loop.
- **A message means what its documentation says.** A message below `WM_USER` is the system's, and every class of the system and of the common controls means by it what the system documents, so a wrapper for one may be sent to any window; Rich Edit is the documented exception (EM_CHARFROMPOS, EM_POSFROMCHAR), and the edit messages it reads otherwise are sent only to an `Edit`. A message from `WM_USER` up is defined by its control class (`LVM_FIRST` and `DTM_FIRST` are both `0x1000`), so its wrapper checks the window's class first (`of_class`) and does nothing for a window of another class.
- **A reply the layer's soundness depends on is asked of the control class's own procedure, never through the subclass chain.** Any safe `subclass::set` closure can answer any message sent to a window. So a reply the layer goes on to follow, size a buffer by, or decide ownership from is had by calling the class's procedure directly (`win::system_class_proc`: for a window of this thread whose class's procedure is the system's; refused otherwise, as for a goz-gui class registered under a control's name): the length that sizes LB_GETTEXT's buffer (`listbox::text`, `combo::text`), the image list a list view shows or gives back (LVM_GETIMAGELIST, LVM_SETIMAGELIST) and the one a tree takes and shows (TVM_SETIMAGELIST, TVM_GETIMAGELIST), a tree's new items and every walk of its items (TVM_INSERTITEMW, TVM_GETNEXTITEM). So does a message whose item a subclass could delete before passing it on (every `tv` message naming an item); another's code's come through the chain, which passes one on only while the tree has its items (above). Any other answer that comes back through the chain is a value that may be wrong, never followed.
- **What the system delivers is what it documents.** A procedure's `lParam` for `WM_NOTIFY`, `WM_DRAWITEM` and the like points at the structure the message defines. Only a [`Msg`](../src/win/msg.rs) the system delivered hands those out, through typed accessors (`m.notify()`, `n.get::<NMLVDISPINFOW>()`, `m.draw_item()`), as a `View`: read-only, but for the structures none of whose fields the system reads back as an address, a length or an index (`msg::Writable`: WINDOWPOS, MINMAXINFO, MEASUREITEMSTRUCT). What a notification asks its procedure to write goes in through a setter that checks the notification and writes through the pointers the system gave (`info.set_text(..)`, `info.set_image(..)`); a custom draw structure's colours and state through setters of their own (`cd.set_text_color(..)`, `cd.set_text_bk_color(..)`, a tree's `cd.set_item_state(..)`), as its control reads its other fields back (a list view its `dwItemSpec`, as the row it goes on to draw). Which structure a `WM_NOTIFY` comes with is told by its header as delivered: the `Msg` copies it once, before any view is lent (a `Notify`'s header is private: `code()`, `from()`, `id()`; no view lends it writable). A `Msg` made with `Msg::new` hands out nothing.
- **Another process of the user is as trusted as goz-gui.** A process of the same user and integrity can send goz-gui's windows any message with any parameters, and the system marshals few of them (`WM_NOTIFY`, `HDM_LAYOUT`, the menu bar's `0x91`/`0x92` and `WM_DROPFILES` arrive with whatever addresses it chose). The layer, like any Win32 program, trusts what its queue delivers: such a process can already do anything goz-gui can. What other programs put on the clipboard is read from a copy, within its size.
- **goz-gui's private messages (`WM_APP` up to `0xC000`) carry no pointers**, and go only to goz-gui's own windows (of this process, handled by a trampoline) and loops (threads that made their queue with `queue::ensure`). A value that has to travel with one goes as a [parcel](../src/win/parcel.rs): the message carries a ticket, and the window claims the value by ticket and by type. `win::post_app_to_other_process` posts to another goz-gui instance, where the message is read.
- **Some undocumented interfaces are as described**: the menu bar's drawing messages and their structures (`menubar`, laid out so since Windows 10 1809); uxtheme's dark-mode exports at ordinals 133, 135 and 136, looked up only on build 17763 or later; a shell folder given an ID list it did not make checks it rather than reading past it.
- **In-process COM servers keep their interfaces' contracts.** The calls here load third-party code into the process: shell extensions (context menu, icon and thumbnail handlers), WIC's codecs, namespace extensions. Like the system, they write no further than the buffers they are given. Code in the process could break any of Rust's promises anyway; this is the narrow part of that trust the layer relies on, written down because it is about code that is not the system's. COM, once initialized on a thread, is never uninitialized (`com::Apartment`), so no object outlives the libraries it runs from. One call more relies on a server's word: `com::Apartment::end_unloading_unused` (CoFreeUnusedLibrariesEx with no delay) unloads the DLLs COM loaded for the calling thread's apartments whose DllCanUnloadNow says they can go. goz-gui makes it as the preview's thread ends, its objects released; it does nothing on a thread whose apartment was kept (the UI thread's) or that made an Explorer context menu, whose handlers are known to answer wrongly (Work Folders' says yes while a thread of its own runs: see `shell::ContextMenu` in `src/shell.rs`). So the assumption is: the COM servers a thread that neither kept its apartment nor made a context menu loads answer DllCanUnloadNow truthfully.

So the rules for a wrapper:

1. **No raw pointer in a safe signature**, in or out. Take `&str`, `&[u16]`, `&RECT`, `&mut` structs or owned values; build the pointer inside.
2. **A structure with pointer fields goes in by value**, and the wrapper sets those fields itself (`lv::insert_item(lv, item, Some("text"))` sets `pszText`; the caller's is ignored).
3. **A buffer the system writes to is the wrapper's own**, sized from what it passes, and copied out.
4. **No generic `send(hwnd, msg, w, l)`**: a message is sent through a function that types its parameters (`lv::item_rect`, `edit::set_sel`). `win::send_plain` takes only the system messages whose parameters are all integers or handles (WM_CLOSE and WM_SYSCOMMAND only to goz-gui's own windows, above); `win::send_app` and `win::post_app` only goz-gui's own, to goz-gui's own windows.
5. **What the system frees is owned**: a kernel handle, a GDI object or DC, an icon, an image list, a theme handle, a hook, a find handle, an accelerator table, an item ID list, a COM object is a type whose `Drop` releases it (`sync::Event`, `process::Process`, `gdi::Owned`, `gdi::MemDc`, `gdi::WindowDc`, `icon::Icon`, `imagelist::ImageList`, `uxtheme::Theme`, `hook::Hook`, `file::Find`, `queue::AccelTable`, `dib::Section`, `shell::Pidl`, `shell::ShellItem`, `shell::DataObject`, `preview::Handler`); a function that makes one returns it so. No safe function deletes, destroys, releases or closes a raw handle, which could be another part of the process's (windows and menus, which user32 checks and which go with their owner, are destroyed by handle: `win::destroy`, `menu::destroy`). Selecting a GDI object into a DC borrows it (`gdi::Selected::new`); the object a selection replaced is a `gdi::Previous`, only selected back.
6. **Flags that say a field holds something are the wrapper's**: a flag whose field the wrapper does not fill, or that makes a call read more than the structure it is given, is masked off (TVITEMW's TVITEMEXW-only fields, LVIF_NORECOMPUTE, TCIF_PARAM, HDI_FILTER, EXTENDED_STARTUPINFO_PRESENT, the CMIC_MASK flags of fields left empty). A template's strings never start with 0xFFFF, read as an ordinal.
7. **Memory the system lends is copied out within the call** (a DIB section's bits, a clipboard global, a shell string): no Rust reference into it outlives the call that got it. A `dib::Canvas`'s or `dib::Section`'s pixels go in and out by copy (`pixels`, `set_pixels`, through GDI, which finds the bitmap by its handle each time), never through a pointer into the section; `clipboard::Clipboard::data` copies a block while the clipboard is open (and `files` reads a file drop from that copy), `shell::DataObject::get` while it holds the medium; a resource is copied out of read-only pages of the data file's own mapping, or of the resource file the loader found the resource in for it (the mapping that holds the resource's entry, its file the module's own `.mui` or `.mun`, mapped while the module is loaded), never out of another module's pages (`resource`).
   A structure a control may write is passed to it as the wrapper's own, mutable (`&raw mut` of a local, never of a binding it borrows or of the caller's `&T`): LVM_GETITEMTEXTW writes the LVITEMW it is given (its mask and item).
8. **Every `unsafe` block has a `// SAFETY:` comment** saying why its preconditions hold (`clippy::undocumented_unsafe_blocks` is on in `win`).

## Procedures are closures

goz-gui gives Windows only the trampolines in `win`; each hands the message to a Rust closure as a `&Msg`.

- **A window**: register its class with `win::class::Class { .. }.register()`, make it with `win::class::create(&Create { .. }, move |m| ...)` (only of a class registered so: another class's procedure would read the handler's address as creation data of its own). The closure gets every message from `WM_NCCREATE` to `WM_NCDESTROY` and is dropped after. `m.def()` is `DefWindowProcW` (but for WM_CLOSE, which it answers with `win::destroy`, waiting while a control in the window is busy). A control goes with `win::class::create_plain` (no MDI client, nor a class by its atom: they read creation data none is given), and so in a template: `Template::control` panics for those.
- **A modal dialog**: build a `Template`, then `t.modal(owner, &|m| proc(&state, m))`. The state lives on the caller's stack; the dialog cannot outlive the call. Answer as a dialog procedure does (nonzero: handled); a `WM_NOTIFY` answer goes in with `dlg::set_result` (a dialog's only: in another window, its offset is that class's). `dialog::common(m, &look)` does what every themed dialog shares.
- **A child dialog** (a page): `t.create_child(parent, move |m| ...)`; the closure owns its state (an `Rc`) and is dropped with the dialog.
- **A subclass**: declare a `static KEY: subclass::Key = subclass::Key::new("what it is");`, then `subclass::set(hwnd, &KEY, move |m| ...)`, for a window of this thread. `m.def()` passes the message on. One subclass per key and window; setting it again replaces it; `subclass::remove(hwnd, &KEY)` takes it off; it goes with the window. A subclass may answer anything, so nothing of the layer's soundness rests on what one answers (see the trust model). `m.def()` passes no message on to a tree view goz-gui keeps track of that names an item the tree no longer has (the subclass may have deleted it): that answers 0.
- **A menu** is shown (`menu::track`) only for one of goz-gui's own windows (`is_goz_window`): the menu loop sends its owner WM_MEASUREITEM and WM_DRAWITEM with the values of the items it draws, a shell handler's among them, which only goz-gui's procedures pass on to the code that filled them.
- **A hook**: `hook::set(Kind::Cbt, |event| ...)`, dropped to unhook. Events are copied out (`Event::Create { hwnd, style }`).
- **A COM object of goz-gui's** (a file operation's progress sink, a preview handler's frame and stream, a window's accessible object) is a private type configured with closures or a Rust value (`shell::ProgressSink::new(|..| ...)`, `preview::Frame::new(context, translate)`, `a11y::AccessibleObject::new(hwnd, elements)`); only a wrapper of its interface is handed out. A method that runs a closure holds a reference to its object meanwhile (`to_object`): the closure may let the last other one go. The accessible object goes to clients behind a front that writes every out-parameter before the call goes on, as `windows`' shims leave one unwritten when a method answers S_FALSE.

A closure that is running is kept alive even if it destroys its own window or removes its own subclass, so it never frees what it is using. A control is not so kept: `win::destroy` waits while one in the window is busy (see the trust model). Outside `class`'s trampoline, which keeps a window's closure there, nothing in goz-gui reads or writes `GWLP_USERDATA`: state lives in the closure.

A message handed on to another of goz-gui's functions goes as the `&Msg` itself (`App::strip_message(m)`, `Page::message(app, page, m)`, `Strip::message(app, m)`, `PaneContent::handle(app, pane, m)`, `ContextMenu::message(m)`), not as its parts: only the `Msg` the system delivered vouches for what its `lParam` points at, and the parts alone vouch for nothing. The thread's message loop takes messages with `queue::get`, which answers `Got::Message` for each and `Got::Quit(code)` at WM_QUIT (or with `queue::take`, which does not wait). A `queue::Queued` is dispatched at most once: `queue::dispatch` takes it by value, and `queue::translate_accelerator` gives it back only when it was not one of the table's keys. `queue::peek` leaves a message in the queue and gives a plain copy.

## Where things are

One module per area of the API; `wnd`'s functions are re-exported at `win::` itself (`win::set_focus`, `win::text`).

- `mod.rs`: the trust model, `send_raw`, class checks (`class_is`, `class_name`, `of_class`), UTF-16 helpers (`wz`, `wz_units`, `until_nul`, `units_as_bytes`), words of a parameter.
- `msg`: `Msg` (a delivered message, its typed accessors, `def`, `paint_next_into`), `Notify`, `View` (read-only but for the `Writable` structures, and its setters).
- `class`, `dlg`, `subclass`, `hook`: the trampolines (windows, dialogs, subclasses, hooks), each handing a closure a `Msg`; `dlg` also has the message box and the colour picker.
- `queue`: the thread's message queue (`get`, `take`, `peek`, `dispatch`, `msg_wait`), goz-gui's own loops (`ensure`, `post_thread`), accelerator tables (`AccelTable`, owned, its entries copied out).
- `parcel`: values that travel with goz-gui's private messages.
- `dropfiles`: files dropped on a window, read while the drop is delivered.
- `wnd`: windows as handles: place, text, state, parent, focus, timers, hotkeys, moves together, goz-gui's own messages (to its own windows, `is_goz_window`), DWM attributes; `destroy`, which waits while a control in the window is busy.
- `busy`: the controls of the thread in the middle of their own processing as goz-gui sees it, and the destruction that waits on them (the message-only window that carries it out).
- `sys`: keyboard and mouse state, the current message's time, metrics, DPI, monitors, caret, sounds, the last error and its text, the system folder and environment, the Windows build.
- `gdi`: device contexts and GDI objects (owned: `MemDc`, `WindowDc`, `Owned`; selected by `Selected`), text, drawing, stretching, fonts; `dib`: 32-bit DIB sections whose pixels are copied in and out (`Canvas`, drawn on in a DC of its own; `Section`, a bitmap of its own), and any bitmap's pixels.
- `uxtheme`: theme data, a control's visual style, the undocumented dark mode.
- `menu`: menus made, filled, read, changed and shown; `menubar`: the menu bar's undocumented drawing messages.
- `scroll`: scroll bars and the wheel.
- Controls, each checking the class before a message from `WM_USER` up: `button`, `combo`, `datetime` (the date picker), `edit`, `header`, `hotkey`, `listbox`, `lv` (list view, and the image lists it holds), `tab`, `tip` (tooltip), `trackbar`, `tv` (tree view: its items as `tv::Item` tokens, kept track of per tree, and the image lists it shows); `imagelist` for image lists, owned (`ImageList`) or the shell's (`SystemList`).
- `icon`: owned icons, the program's and the system's, the shell's file and stock icons.
- `shell`: the shell. In `mod.rs`: shell items and their icon handlers, item images (`ImageFactory`), file information, settings, associations, known folders, ShellExecute, recent documents, Properties, the tray icon. `pidl`: item ID lists (`Pidl`), the shell's folders (`Folder`), opening a folder with items selected. `data`: data objects (`DataObject`: read and written by copy, the OLE clipboard's, dragged out). `menu`: the Explorer context menu (`ShellMenu`). `dialog`: the common item dialogs. `fileop`: file operations and their progress sink. `link`: shortcuts, property stores, the jump list.
- `preview`: preview handlers (`Handler`), the frame they pass keys to (`Frame`) and the read-only stream they read a file through (`Stream`).
- `wic`: the Windows Imaging Component: decoders, frames, scaling and conversion, pixels copied out.
- `a11y`: accessibility (MSAA) for what a window paints itself: an accessible object that adds painted parts to the system's standard one.
- `file`: attributes, times, names, listings (`Find`), owned file handles, drives, `file:` URLs.
- `clipboard`: the clipboard, opened by a guard; its sequence number and registered formats.
- `process`: processes and threads, named mutexes, a named pipe read and written overlapped, services.
- `reg`: the registry, its keys named as text or in UTF-16.
- `resource`: resources of a program or library loaded as data.
- `locale`: normalization, comparisons, case, code pages (the ANSI one decoded), the user's date and time formats; `time`: the clock and time conversions.
- `com`: COM apartments (never uninitialized), and OLE.
- `sync`: kernel events.

## Adding a wrapper

Put it in the module of its API (`lv.rs` for list-view messages, `gdi.rs` for GDI, `com.rs` for COM apartments and the like), with a `///` line saying what it does, and a test where it can be tested without a desktop (`trampolines_tests.rs` makes message-only windows and dialogs that never show). Add it when something uses it: the layer has no dead code (`win` allows none), so a wrapper nothing calls is deleted, not kept for later. The one exception is a wrapper that serves only as a test's oracle (Windows' own answer that goz-gui's is checked against: `locale::format_byte_size`, `shell::command_line_to_argv`), which is `#[cfg(test)]`.
